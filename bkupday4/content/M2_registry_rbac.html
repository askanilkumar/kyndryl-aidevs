One file that tells your agent what it may touch, and your SOC team how.

The registry

Flat JSON. Easy to review, easy to audit, easy to diff in Git.

{
  "tools": {
    "kb_search":     {"risk": "low",  "requires_approval": false, "allowed_roles": ["viewer","engineer","supervisor"]},
    "ticket_lookup": {"risk": "low",  "requires_approval": false, "allowed_roles": ["engineer","supervisor"]},
    "tower_status":  {"risk": "low",  "requires_approval": false, "allowed_roles": ["engineer","supervisor"]},
    "plan_change":   {"risk": "high", "requires_approval": true,  "allowed_roles": ["supervisor"]}
  }
}

Where RBAC fires in the agent

plan → guard → execute → plan …
       ↓ denied
       loop back

The guard node runs before every tool call. It checks the registry. If denied, the result is a DENIED line in history — not a tool call. The LLM sees the denial on the next loop and chooses something else (or stops).

Design choices to defend

Why is ticket_lookup not viewer-safe?
Internal incident details reveal ongoing outages. A customer-facing viewer should not see "3 towers down in Chennai North" before NOC confirms.
Why only supervisor on plan_change?
Changes customer billing. Even without a bug, an over-helpful engineer could cost real money. One role, one approval gate.

Pitfalls

  • Role sprawl — stop at 3–5 roles. 20 role names is a smell.
  • God tools — one tool that "does everything" cannot be governed. Split by risk.
  • Hidden policy — if the policy lives inside Python if-statements, you lost. The registry is the single source of truth.
Where should this live in a real deployment? Keycloak, OPA, or a service you already run. The shape of the registry doesn't change — just where it is served from.
