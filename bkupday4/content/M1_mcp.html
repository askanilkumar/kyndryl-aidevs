M1 · Why MCP

Model Context Protocol — the one wire between agents and their tools.

The problem

BEFORE

You wrote a Python function for each tool. Then another agent wants the same tool, so you wrap it again. Then a Go service wants it, so you re-wrap. Three teams, three implementations, three ways to break.

AFTER

Each tool lives in one MCP server. Any agent — Python, Go, Claude Desktop, your in-house framework — speaks the same two endpoints. One server, N clients, zero re-implementations.

MCP in one picture

The two endpoints

GET  /tools/list                        → list of tools + schemas
POST /tools/call  {name, args}          → {ok, result}

Real MCP has a few more (resources, prompts, sampling), but these two carry 90% of the signal. Our server is a thin FastAPI app that implements exactly this shape.

What MCP does NOT give you

  • Auth — you add it (API key, OAuth, mTLS)
  • Role-based access — you add a registry (next module)
  • Approval — you add HITL (module after)
  • Rate limits, cost caps — you add them in a gateway in front
When would you NOT use MCP? If the agent and tool live in the same process and will never be re-used elsewhere, a plain Python function is enough. MCP is for tools you want many agents (or many teams) to share.
