Cycle 1 · 60 min

Security and guardrails

The idea

  • A model follows text. An attacker writes text. So the model can be talked out of its rules (prompt injection).
  • A guardrail is a check in code, before and after the model. Same input → same decision, every time.
  • Three things to protect: the instructions (injection), people's data (PII), company data (internal docs).
  • Plus action safety from Day 4: tool allow-list, write actions need human approval, loop limit.

Layers, not one wall

LayerCheap and fastSmarter (production)
Injectionregex patterns (our lab)Llama Guard, NeMo Guardrails, Azure Prompt Shields, Bedrock Guardrails
Harmful content—OpenAI moderation (free, toggle in our app)
PIIregex for phone / email (our lab)Microsoft Presidio
Data leaksmarker check on tool output + answer (our lab)document-level access control in RAG (filter before retrieval)
Use guardrails when
  • users are outside your team
  • the agent can call write tools
  • data has PII or internal content
Don't rely on them when
  • you think one regex = secure
  • a guard blocks so much that real users can't get help (false positives)
  • you skip access control because "the prompt says never share"
Key line: "The prompt is a request. The guard is a rule."

Cycle 2 · 60 min

Tracing and observability

The idea

  • Normal apps log errors. AI apps can be wrong without an error: a polite, confident, wrong answer.
  • A trace records one request step by step. Each step is a span: input, output, time, tokens, cost.
  • With traces you can answer: Which tool did it call? Why so slow? Why so expensive? What did the model actually see?
LangSmithLangfuse
FromLangChainopen source (MIT core)
Self-host on-prementerprise planyes, free
Strong inLangChain / LangGraph apps, datasets, experimentsany stack, cost tracking, prompt management
Standardboth accept OpenTelemetry, so you are not locked in
Trace when
  • always in production (sample if traffic is huge)
  • debugging a wrong answer
  • cost reviews (FinOps)
Be careful
  • traces store prompts: mask PII before tracing
  • regulated data may not leave the country → self-host
  • don't trace secrets or full documents
Key line: "If it isn't traced, it didn't happen — and you can't fix it."

Cycle 3 · 50 min

Evals and monitoring

The idea

  • Evals = unit tests for an AI app. A fixed set of questions with "what good looks like". Run before every release.
  • Safety cases (attacks, write actions) must pass 100%. Quality cases need a pass rate (we use 80%).
  • Monitoring = the same idea on live traffic: latency, p95, cost, block rate, error rate, with alert limits.
How to gradeGood atWatch out
Rules (tool used, word present)free, exact, fastmisses tone and quality
LLM-as-judgequality, helpfulnesscosts tokens, can be biased; check it against humans
Human reviewhard and new casesslow, expensive
Good eval habits
  • every bug becomes a new case
  • keep the set small and fast (runs in CI)
  • track pass rate per version
Common mistakes
  • only "happy path" questions
  • one big average score that hides a safety failure
  • alerts nobody reads
Key line: "No evals, no release. No monitoring, no sleep."

Cycle 4 · 40 min

LLMOps / AgentOps

The idea

  • DevOps for AI. The "code" of an agent is prompt + model + tools + guards + data. Any of them can break it.
  • So each one is versioned, tested by the eval gate, released with a record, and rolled back fast.
  • AgentOps adds: watch tool calls and approvals, cost per conversation, loop limits, and who changed what.
edit v2→evals→gate→release→monitor→rollback?
In real teams
  • prompts in git (or a prompt registry like Langfuse Prompts)
  • eval gate runs in CI (GitHub Actions) on every pull request
  • canary: 5% of traffic to v2 first
Anti-patterns
  • editing the prompt in production "just a little"
  • changing model and prompt in the same release
  • no way back to the last good version
Key line: "A prompt change is a code change."

Cycle 5 · 90 min

Deploy on the cloud: Azure and AWS

The idea

  • Same code, new home. What changes is only where the keys come from (env vars) and who can open it (password, network rules).
  • PaaS (Azure App Service): you give code, Azure runs it. IaaS (AWS EC2): you get a server and run it yourself.
Azure App ServiceAWS EC2Also know
Deployaz webapp upgit clone + pip + systemdcontainers: Azure Container Apps, AWS ECS Express Mode
You managecode + settingsOS, patches, restartsserverless agents: Bedrock AgentCore, Azure AI Foundry Agents
KeysApp settings (→ Key Vault)/etc/asknova.env (→ Secrets Manager)never in git
Accesspassword + HTTPS by defaultsecurity group: 8501 from My IPproduction: private network + SSO
Pick PaaS when
  • a normal web app or agent
  • small team, no ops people
  • you want HTTPS and scaling for free
Pick a VM when
  • you need custom software or a GPU (vLLM, Day 1)
  • strict network or OS control
  • but then you own patching and uptime
Key line: "Deploy is the start of operations, not the end of the project."
