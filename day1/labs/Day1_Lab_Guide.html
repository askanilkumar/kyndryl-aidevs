What you are building

Your teammates call your gateway with their own keys. Your gateway calls the central one with a single team key. Nobody holds a raw cloud key.

  1. Plan 10 min

    • Write the IP address of your team VM and of the central gateway on a sticky note or in NOTES.md.
    • Agree on three things before touching a keyboard: the alias names your team will expose (team-chat, team-chat-b), who gets which key, and what budget and request limit each key gets.
    • Test you can reach the team VM from your own VM: ssh <user>@<team-vm-ip>.

  2. Install Docker and copy the gateway files 15 min

    First log in to the team VM from your own VM: ssh <user>@<team-vm-ip> (type yes the first time, then the password from your team card). Then, on the team VM:

    team VM
    curl -fsSL https://get.docker.com | sudo sh

    From your own VM, copy the starter folder across:

    your VM
    scp -r ~/day1-labs/team <user>@<team-vm-ip>:~/gateway
    Common problems: Docker install and file copy
    • docker: permission denied: run newgrp docker, or log out and back in.
    • The install script hangs or times out: the VM has no internet. Tell the trainer. Test with curl -sI https://get.docker.com | head -1.
    • scp says "No such file or directory": the team folder is under ~/day1-labs/ on your VM. Run ls ~/day1-labs/team first.
    • docker compose not found: the install did not finish. Run the install line again and read the last 10 lines.

    Back on the team VM, create the secrets file and fill it in:

  3. Start the gateway and send the first request 10 min

    team VM
    docker compose up -d
docker compose logs -f litellm

    The first start takes a minute or two while the database is prepared. Press Ctrl+C to leave the logs once you see the server running.

    team VM
    export GW=http://localhost:4000
export MK=$(grep LITELLM_MASTER_KEY .env | cut -d= -f2)
curl -s $GW/health/liveliness
curl -s $GW/v1/chat/completions -H "Authorization: Bearer $MK" -H "Content-Type: application/json" \
  -d '{"model":"team-chat","messages":[{"role":"user","content":"Reply with the word ready"}],"max_tokens":10}'

    You should get a JSON answer. If you get an error, read the last 20 lines of the logs before you change anything.

    Common first-start problems
    • Connection error / 401 from upstream: UPSTREAM_BASE must end in /v1, and the team key must be exactly as on your card.
    • "model not found" for the upstream: the name after openai/ in config.yaml must match what the central gateway lists: curl <central>/v1/models -H "Authorization: Bearer $UPSTREAM_KEY".
    • After editing config.yaml: docker compose restart litellm.
    • Edited .env? Use docker compose up -d --force-recreate litellm.
    • Container keeps restarting: run docker compose ps, then docker compose logs --tail 30 litellm. A YAML error is nearly always a wrong indent. Use spaces, never tabs.
    • Database not healthy: check DB_PASSWORD in .env has no spaces or quotes. If you changed it after the first start, run docker compose down -v and start again.
    • Curl from your own VM times out but it works on the team VM: port 4000 is blocked between the VMs. Tell the trainer.
    • Answer works but spend stays $0: the two *_cost_per_token lines are missing or wrong in config.yaml.

  6. Failure Lab: break it on purpose 25 min

    A gateway you have only seen working is a gateway you do not understand. Run all five tests on the team VM. For each: predict what will happen, run it, then set the result and write what you saw.

    Test 1 · A dead model, and a fallback that saves the user

    Add this block to model_list in config.yaml, and extend fallbacks so it reads as shown. Then restart.

    config.yaml (add under model_list)

    team VM

  -d '{"model":"team-dead","messages":[{"role":"user","content":"Reply with the word ready"}],"max_tokens":10}'
docker compose logs --tail 40 litellm

    Expected: an answer still arrives. The logs show the failed attempts first, then the fallback. Note the extra seconds the user waited.

    Test 2 · A leaked key is revoked

    team VM
    K=$(mk_key victim)
curl -s $GW/v1/models -H "Authorization: Bearer $K" | head -c 200; echo
curl -s $GW/key/delete -H "Authorization: Bearer $MK" -H "Content-Type: application/json" -d "{\"keys\":[\"$K\"]}"; echo
curl -s $GW/v1/models -H "Authorization: Bearer $K" | head -c 300; echo

    Expected: the key works, then fails with an authentication error. Think: how long would it take to do the same to a raw cloud key that is pasted on six VMs?

    Test 3 · The rate limit

    team VM
    K=$(mk_key limited 3)
for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w "call $i -> HTTP %{http_code}\n" $GW/v1/chat/completions \
    -H "Authorization: Bearer $K" -H "Content-Type: application/json" \
    -d '{"model":"team-chat","messages":[{"role":"user","content":"hi"}],"max_tokens":5}'
done

    Expected: the first three succeed, the next ones return 429. What would a user see in Copilot when this happens?

    Test 4 · The budget runs out

    team VM
    K=$(mk_key tiny 60 0.0005)
for i in $(seq 1 8); do
  curl -s -o /dev/null -w "call $i -> HTTP %{http_code}\n" $GW/v1/chat/completions \
    -H "Authorization: Bearer $K" -H "Content-Type: application/json" \
    -d '{"model":"team-chat","messages":[{"role":"user","content":"Write 150 words about mobile towers."}],"max_tokens":200}'
  sleep 6
done

    Expected: early calls succeed, later calls are refused with a budget error. Spend is written in small batches, so the cut-off arrives a call or two late. Why does the config file need input_cost_per_token for this to work at all?
